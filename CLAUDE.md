# Everything Shul — project context for Claude Code

This file exists so a fresh Claude Code session (no memory of the Cowork chat that built this
project) has enough context to keep working without re-asking the basics. Read this before
making changes.

## What this is

A static marketing/portfolio site for **Everything Shul**, a company that builds software for
shuls/nonprofits. It showcases six products the company built. No framework, no build step,
no dependencies — plain HTML/CSS/JS meant to be dropped straight into any static host (GitHub
Pages, Netlify, etc.) or a git repo.

Contact email used throughout the site: `everythingshul@gmail.com`.

## File structure

```
index.html          Home page. GENERATED by tools/build.py (edit the data/templates there, then re-run)
contact.html          Contact page, also generated by tools/build.py. Form posts to the Brevo worker.
share/<id>/index.html  One tiny page per project carrying its Open Graph thumbnail tags; the share
                        buttons share these URLs, and humans are redirected to /#<id>. Generated too.
css/style.css          All styling. CSS custom properties at the top define the theme.
js/main.js             Nav, mobile drawer, auto-panning screenshot reels, preview-video play/pause on
                        scroll, full-tour lightbox, share buttons, contact form handler.
assets/logo-light.png   Logo recolored for dark backgrounds (site + emails). assets/logo.png is the
                        original navy/cyan version.
assets/fonts/           Self-hosted Newsreader (headlines) and Instrument Sans (text).
assets/share/           1200x630 share thumbnails, generated by tools/og.js.
assets/video/           Product tours (originals) + preview loops + poster frames.
worker/                 Cloudflare Worker that sends the contact emails through Brevo.
worker/chat/            Cloudflare Worker for the chat's human handoff (KV storage, Brevo emails, admin API).
js/chat.js              Chat widget + matching engine for "Chesky". js/chat-kb.js is his knowledge base
                        (GENERATED by tools/kb.py from ~300 stored replies; edit tools/kb.py, not the .js).
js/chat-config.js       One line: window.ES_CHAT_ENDPOINT = the deployed chat Worker URL (empty until deployed).
js/metrics.js           First-party, cookie-less analytics tracker (posts to the chat Worker POST /t, stored in D1).
js/voice.js             Voice notes (record + playback, WhatsApp style) used by the chat and the contact form.
js/invoice-doc.js       Renders an invoice/quote document (customer pay page + admin). css/invoice.css styles it (always a white sheet).
pay/                    The customer's invoice page (pay/index.html + pay.js): view, pay with Stripe, accept a quote, print.
privacy.html            Public privacy page (generated by build.py); linked from the footer.
admin/                  Password-protected inbox where the team answers handoff chats (talks to worker/chat).
tools/                  build.py (pages), kb.py (Chesky's replies), og.js (share thumbnails). Dev-only; the site has no build step.
```

To change project copy, order, links or media: edit PROJECTS in tools/build.py, run
`python3 tools/build.py`, and if a poster/screenshot changed, `node tools/og.js`
(needs Playwright; set PLAYWRIGHT_PATH if it is not on the default path). Commit the output.

## Theme

Dark theme (client prefers it; do not switch back to a light theme): near-black navy background
(`#0a0f1a`), panels `#0d1526`/`#121d35`, light text, cyan `#25a9ea` buttons with dark text, brand
navy `#2f5596`. Newsreader serif headlines, Instrument Sans body (self-hosted). The layout is
deliberately editorial: no glass cards, icon tiles or fake browser chrome. The client asked for a
design that does not look AI-generated, and ALSO wants lots of animation: headline words sliding in,
staggered scroll reveals, wipe-in media, parallax, drifting glow, a project-name ticker, a scroll
progress bar, hover effects (all in css/style.css "motion" section + js/main.js; reduced-motion safe).
Keep adding motion in that spirit. Showcase cards stay side by side on phones (explicit client request; feature lists are
hidden there to make room).

**Never state a project count in copy** (e.g. "six platforms"): the client keeps adding projects.

Wording note: the site intentionally says "organization"/"organizations", never "community" —
this was an explicit client correction earlier in the project. Also intentionally has **no**
decorative pills, dashes before eyebrows, stat badges ("24/7 support", "5 shipped", "100% for
non-profits") — all were explicitly removed per client request. Don't reintroduce them.

## Video showcase pattern

For DRM / Kipas Hair BP / Kupes Hair Williamsburg, each showcase card uses `.video-frame`
(same browser-chrome look as `.browser-frame`, i.e. the dots + URL bar) wrapping a
`.video-stage` containing:
- a muted, looping `<video class="preview-video">` using `assets/video/{key}-preview.mp4`
  (silent, ~12s, 960px wide) with `poster="assets/video/{key}-poster.jpg"`
- a `.play-full` button (`data-video="assets/video/{key}-tour.mp4"` `data-title="..."`) that
  opens the **full, original, audio-on** tour video in a lightbox (`#video-lightbox` at the
  bottom of `index.html`, wired up in `main.js`)

`main.js` pauses/plays preview videos based on viewport visibility (IntersectionObserver) to
save bandwidth, and handles opening/closing the lightbox.

**Important judgment call, keep it this way unless the client says otherwise:** the preview
loops and poster frames were deliberately cropped to aggregate/dashboard moments of the videos
(totals, charts, stats) rather than screens that expose a real individual's personal contact
info. The DRM source video at one point opens a specific donor's profile card showing their
full name, phone number and email — that segment was avoided for the *always-visible autoplay
preview and poster*, but the full unedited tour video (used only on explicit click via "Watch
full tour") was left intact since it's the client's own footage and their call to include it.
If asked to change the preview/poster segments, keep this PII consideration in mind.

Full tour videos (`*-tour.mp4`, all four products) are the client's original recordings with
sound, used unedited (1920x1080, AAC audio) — do not re-encode or trim them; re-encoding earlier
stripped the audio. Only the silent ~12s preview loops (`*-preview.mp4`, DRM/Kipas/Kupes) and
the poster frames were generated with ffmpeg.

## Logo

`assets/logo.png` is **not the original logo file** — the original was lost (see "Known gaps").
It was reconstructed by extracting a sharp frame from the DRM tour video's branded splash
screen (the video opens on an "Everything Shul / DRM / Donor Relationship Manager" splash),
cropping tightly around the white logo card, upscaling, and converting the white background to
transparency via a white-distance alpha mask. It's legible but a bit soft compared to a vector
original. **If the client ever provides the original logo file (e.g. a clean PNG/SVG with no
background), replace `assets/logo.png` with it** — it'll look noticeably crisper in the navbar
and footer.

## Status / open items

1. **Showcase media:** DRM, Kipas Hair BP, Kupes Hair Williamsburg and Mamudem use real product-tour
   videos (originals, with sound, unedited). JListings and Fundraise Wall use auto-panning
   screenshots (`assets/screenshots/*-full.png`). The old "Preview coming soon" placeholders are gone.
2. **Domain:** `everythingshul.com` is registered at Squarespace Domains (nameservers
   `*.squarespacedns.com`) and points at GitHub Pages via the four `185.199.108-111.153` A records
   plus a `www` CNAME to `everythingshul.github.io`. Do not re-add the old Wix records.
3. **Contact emails:** `worker/` (Cloudflare Worker + Brevo) is written but only works once it is deployed.
   Use `tools/deploy-workers.sh` (needs CLOUDFLARE_API_TOKEN + CLOUDFLARE_ACCOUNT_ID in the environment);
   the client types BREVO_API_KEY (both Workers) and ADMIN_TOKEN (chat) directly into Cloudflare's dashboard as
   Worker secrets, so they never pass through Claude. Emails are sent from support@mail.everythingshul.com (the
   mail.everythingshul.com domain must be authenticated in Brevo; SENDER_EMAIL in both wrangler.toml files).
   Every email sets Reply-To to the Gmail inbox, and the team's chat replies are BCC'd there too. Until then the form falls
   back to opening the visitor's email app. If the Worker URL differs from the guess in
   `ENDPOINT` in `js/main.js`, update it.
4. **Logo:** `assets/logo.png` is the sharp logo taken from kipashairbp.org's footer.

5. **Chat bot ("Chesky"):** a friendly illustrated Hasidic man (assets/chesky.svg: black kippah, beard,
   long curled peyos, white button-down; keep the depiction respectful, never caricatured). The header
   says just "Chesky" with an "Online" status (client asked not to call him "Everything Shul's
   assistant"). He is NOT a live AI: the client explicitly chose stored replies. tools/kb.py holds ~360
   keyword-matched replies (including lots of random/personality questions); js/chat.js matches the
   visitor's words (typo tolerant, light stemming) and also has little tools: math, today's date/time, the
   Hebrew date, coin/dice/random number, rock-paper-scissors, "pick A or B", and a few Hebrew/Yiddish words.
   Honesty rule for new replies: only state facts that are on the site; for price, timing, security,
   integrations and anything unknown say the team will answer and offer the handoff.
   **Learning (team-approved only):** answers get thumbs up/down; questions he can't answer and thumbs-downs
   are logged anonymously (emails/phones scrubbed) to the Worker. In /admin/ -> "Teach Chesky" the team
   writes an answer once, or ticks "Also teach Chesky" when replying to a chat, and he uses it for similar
   questions from then on (taught answers beat built-in ones; they can be edited or forgotten). Visitors can
   never add answers themselves. Replies sent from Gmail directly are not seen by the system; only replies
   sent from the admin page teach him.
   **Handoff:** when stuck (or asked for a person) the visitor leaves an email; the team replies from /admin/;
   the visitor sees it in the chat and gets it by email (worker/chat, see its README). Until the client
   deploys that Worker (KV + Brevo key + ADMIN_TOKEN) and sets js/chat-config.js, the handoff falls back to
   opening the visitor's email app and nothing is logged or learned.
6. **Favicon:** the logo on a dark square; icon links carry `?v=3` to bust browser caches. Bump the
   number in tools/build.py if the icon changes again.

7. **Analytics:** first-party and cookie-less. js/metrics.js -> Worker `POST /t` -> Cloudflare D1 (`STATS`,
   database `everythingshul-stats`, schema in worker/chat/schema.sql) -> dashboard in /admin/ (Analytics tab:
   admin/analytics.js, Worker code in worker/chat/stats.js). No IPs stored (daily salted hash), DNT/GPC honored, bots
   ignored, 13-month retention (cron purge), weekly digest email Mondays (`DIGEST` var). Needs the D1 database created
   (tools/deploy-workers.sh does it if the API token has Account > D1 > Edit); until then /t is a no-op and the tab
   shows a setup note. If tracking changes, update privacy.html in tools/build.py and the chat_privacy reply in tools/kb.py.

8. **Voice notes:** the chat (mic button) and contact form ("Or record a voice note") record in the browser (js/voice.js),
   convert to 16 kHz mono WAV and send base64 in the JSON. Chesky can't listen, so a voice note in the bot chat opens the
   team handoff with the note attached. Chat Worker stores audio in KV (`voice:<id>`, served at GET /voice, same TTL as the
   conversation) and attaches it to the team email; the contact Worker only attaches it to the email (Brevo cannot attach .webm).
   Max 60 s / ~2.4 MB. On phones the chat panel is sized to the visual viewport while the keyboard is up (fitKeyboard in js/chat.js).

9. **Customers + billing (CRM, invoices, quotes, Stripe):** admin tabs Customers and Billing (admin/crm.js, admin/billing.js, admin/ui.js).
   Backend in worker/chat/billing*.js on a second D1 database (`BILL`, worker/chat/billing.sql). Money is integer cents; the server
   recomputes all totals. Invoices are emailed with a secret link to /pay/; online payment is Stripe Checkout and the webhook
   (`/stripe/webhook`, signature verified, idempotent) records the payment. Secrets typed into Cloudflare by the client:
   STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET. Daily cron makes repeating invoices and sends reminders. Wix import is a CSV
   column-mapping wizard (Billing -> Import). Contact form and chat handoffs create CRM leads automatically (the contact Worker
   shares the BILL database). Keep copy about money neutral and do not store card data (Stripe handles it).

## Deploying

Static site, zero config. The pages are generated with python3 tools/build.py but committed, so hosting needs no build.
step, no `npm install`, nothing to compile.
